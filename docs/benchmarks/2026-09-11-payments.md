# Payments — what holding the fare adds to dispatch

**Status** harness ready, not yet run. Nothing below is a measurement; the
result section is empty until `make bench-payments` has been run and its output
pasted in.

**Under test** rider booking → trip (`payment_pending`) → `trip_outbox` →
`trip.lifecycle` → **payments (fake processor)** → `payments_outbox` →
`payment.events` → trip → `MatchRequested` on `geo.events`

With `TRIP_REQUIRE_PAYMENT` off, trip asks the matcher for a driver inside the
booking call. With it on, the booking waits while three hops happen, each across
Kafka and each behind an outbox relay that polls every 100 ms when idle:

1. trip's relay publishes `TripRequested`;
2. payments places the hold, and its relay publishes `PaymentAuthorized`;
3. trip consumes that, moves the trip to `requested`, and asks the matcher.

The question is what that costs a rider between tapping Book and a matcher
hearing about them, and which hop the cost lives in.

## Method

`make bench-payments RPS=5 DURATION=2m`, which runs `scripts/bench-payments.sh`:

- **Unheld run.** payments stopped; trip restarted with
  `TRIP_REQUIRE_PAYMENT=false`.
- **Held run.** payments started with `PAYMENTS_PROCESSOR=fake`; trip restarted
  with `TRIP_REQUIRE_PAYMENT=true`. Both consumer groups are waited on until
  their lag is zero, so the unheld run's bookings — payments' backlog — are
  settled before the clock starts.
- Each run books through trip's gRPC as 50 riders, at `RPS` bookings a second
  for `DURATION`, with one seed for both runs so both book the same pickups in
  the same order. Seven pickups in ten are near the simulator's hotspots.
- Held riders save a card first. On the fake processor that is the test Visa
  that always authorizes, so a hold costs the system's time, not a bank's —
  and five bookings a second would meet Stripe's test-mode rate limit before
  it met anything of ours.
- The clock starts at `CreateTrip`, after the quote: routing a quote is
  Valhalla's time and identical in both modes.
- Every stage is timed from the Kafka record it leaves behind, read from the
  end offsets listed before the first booking — not a consumer group, which
  resolves "the end" whenever it joins and could miss the first bookings.
- No matcher and no fleet. Dispatch is the `MatchRequested` trip writes to
  `geo.events`, and payments sits in front of that, not behind it.
- Every booked trip is cancelled afterwards as its rider, which releases the
  hold. trip is put back on `.env`'s settings however the script exits.

The script also reads each outbox relay's own lag histogram from Prometheus for
the held run's window. Prometheus picks up the payments target (`:9107`) only
after a restart: `docker compose -f deploy/compose/docker-compose.yml restart
prometheus`.

A run counts if every booking was either dispatched or refused within the 30s
drain, and the booking rate kept up with `RPS`. The tool reports undispatched
trips and booking errors separately so neither hides in a percentile.

## Result

Not yet run.

| stage                                     | unheld p50 | unheld p99 | held p50 | held p99 |
| ----------------------------------------- | ---------: | ---------: | -------: | -------: |
| booking call                              |            |            |          |          |
| booked → TripRequested relayed            |            |            |          |          |
| TripRequested → PaymentAuthorized relayed |          – |          – |          |          |
| PaymentAuthorized → MatchRequested        |          – |          – |          |          |
| **booked → MatchRequested**               |            |            |          |          |

**Expectations to check, not results.** Each idle relay adds up to one poll
interval, so two relays on the path suggest something on the order of 100–200
ms at the median before any processing. If the held p50 is far above that, the
cost is not the relays; if it is at that and the tail is long, a poll interval
or `LISTEN/NOTIFY` on the outboxes is the lever.

## Caveats

- **The fake processor answers in microseconds.** Stripe's `PaymentIntent`
  create-and-confirm takes hundreds of milliseconds; this measures what the
  architecture adds, and a real hold adds Stripe's own latency on top.
- **One laptop.** Redpanda, Postgres and all services share it.

## Reproducing

```sh
make up-core && make migrate
make bench-payments RPS=5 DURATION=2m
```

Raw results are written to `/private/tmp/bench-payments-{false,true}.json`.
